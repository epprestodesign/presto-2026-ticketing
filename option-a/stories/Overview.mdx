# Aug 4 Changes

The single overview for the **August 4 prototype work**. Three versions are in play —
**Option A** and **Option B**, two shapes of the same configure-then-book journey, and
**Option C**, the one-click grid built in response to the Aug 4 feedback on both.
Everything about all three is documented on this page. Component stories sit under
**Option A**, **Option B** and **Option C** in this same category.

All three are working copies of the Hotel + Packages experience, forked on
**August 4, 2026**; none of them modifies the design system.

> **Start with Option C.** A and B were built before the feedback landed. C is the answer to
> it: a 6-tile grid, no filtering, no modal, ticket free with the room. A and B are kept
> because their detailed configure-and-adjust UI is explicitly *"good for later, not the
> landing page"* — worth having when the package options expand.

### Why Option C exists

The Aug 4 feedback asked for a grid over a scrolling list, packages above the fold, and a pure
one-click purchase with no filtering and no options — with the party size, capped by room
occupancy, as the only variable. Option A is the closer of the two starting points (it at least
opens on packages), but both render the library's Browse Packages page: a filter rail plus a
scrolling list, each row opening a configuration modal. Option C replaces that landing page
outright and keeps the rest of the journey.

Full detail is on the [Option C overview](?path=/docs/aug-4-changes-option-c-overview--docs).

## What changed

**The event.** Pittsburgh Steelers at New England Patriots · Sun, Sep 20, 2026 ·
1:00 PM · Gillette Stadium, replacing the library's Patriots v Bills sample
throughout — hero imagery, browse headers, packages, checkout and confirmation.

**The flow.** A and B both drop the Package Details *page* — everything about a
package lives in a full-screen modal — and differ in what you decide first. C
drops the modal too, and asks you to decide almost nothing.

**Option C — one-click grid** (the Aug 4 feedback response):

```
                              ┌─ Ritz-Carlton ─▶ [choose your room]  ─┐
Package board ──▶ Select ─────┤                                       ├──▶ Checkout ──▶ Confirmation
   (landing)                  └─ Courtyard ────▶ [confirm package]  ──┘
      │
      ├─ dates + guests ─────▶ re-prices all six tiles live
      └─ hotel NAME ─────────▶ Hotel Details (new tab, read-only)
```

The board **is** the landing page — no hero-then-search step, so packages are the
first thing on screen. Six tiles: 3 ticket tiers × 2 contracted hotels, one row
per property.

Selecting a tile raises **one dialog that does one of two jobs**, decided by the
hotel: the Ritz-Carlton carries five contracted room types so it offers the
choice; the Courtyard carries one so it is pure confirmation of the final
package. Either way it *confirms* rather than *configures* — the tier, the hotel
and the free-ticket model stay baked into the tile.

Dates and guests live in one booking widget above the board (Option A's widget
fork, minus the Search button) because both re-price all six tiles at once.
Nights multiply the room and nothing else; occupancy caps tickets per room, and a
larger party books a second room rather than being refused.

Stepper: **Packages · Review**, hidden on the board itself — before anything is
selected it is a progress bar for progress not yet made.

**Option A — packages first:**

```
Landing ──▶ Browse Packages ──▶ [package modal] ──▶ Checkout ──▶ Confirmation
                                      │
                                      └─▶ Hotel Details (new tab, read-only)
```

Stepper: **Packages · Review**. Browse Hotels sits outside the journey; Hotel
Details opens in a new tab as a read-only reference with every booking CTA
suppressed.

**Option B — hotel first:**

```
                    ┌─ Select a package ─▶ Packages (scoped to that hotel) ─┐
RSVP ──▶ Hotels ────┼─ hotel NAME ───────▶ Hotel Details (one room) ────────┼─▶ Checkout ──▶ Confirmation
                    └─ Skip / no hotel ──▶ Packages (tickets only) ─────────┘
```

Stepper: **Hotel · Package · Book**. Step 2 uses the Browse Hotels results layout
trimmed to the two hotels this event holds, with a compact event bar in place of
the page hero so both cards clear the fold.


**Two shapes of package.** Of nine SKUs, five include a stay and four are
package-only. A row shows its rooms line only when there is one.

## Live pricing

**Options A and B — the bundle model.** Nothing about a package is fixed. Tier,
party size, hotel, room type and paid extras all re-price it, following the
library's own convention:

```
components = tier.price × guests  +  room.nightly × nights  +  experience value
package    = round(components × (1 − bundle discount rate))
total      = package + paid extras          ← add-ons sit outside the bundle
```

So *Legends Stadium Tour* is **$604** in Upper Level for two, **$1,074** in Club
Level for two, and **$2,929** in Club Level for eight. The same numbers flow to the
cart, checkout and confirmation.

**Option C — the free-ticket model.** The pitch is inverted: you are not buying a
discounted bundle, you are buying a **room** and the tickets come with it.

```
rooms   = ceil(guests / room occupancy)     one room only sleeps so many
price   = nightly × nights × rooms          ← what's charged
value   = price + ticket face × guests      ← struck through
saving  = ticket face × guests              ← "N tickets free"
```

Nights multiply the room and **nothing else**, so a three-night stay triples the
price and leaves the saving untouched. The nightly rate is the contracted rate
plus a tier uplift of roughly half the ticket's face value — which is why the
same hotel costs more with a Club Level ticket than a Mezzanine one.

| | Club Level | Lower Level | Mezzanine |
| --- | --- | --- | --- |
| **The Ritz-Carlton** · Carlton Suite · sleeps 4 | $809 | $729 | $639 |
| **Courtyard by Marriott** · Double Queen · sleeps 4 | $479 | $399 | $309 |

*One night, two guests. The board re-prices from the dates and party size above it.*

## How the library stays untouched

No prototype here edits `src/`. Options A and B use two mechanisms in their
`vite.config.js`, in that app's build only:

| Mechanism | Used for |
| --- | --- |
| **`resolveId` overrides** | Redirect a library file to a local fork wherever it's imported — `BookingWidget`, `PackageResultCard`, `PackageQuickViewDialog`, and the shared hero image. |
| **Source patches** | Surgical find/replace on read, for the handful of spots that aren't prop-driven: the Browse Hotels event header, the "Who's Attending?" heading, two-way Guests on the packages page, `maximized` + slide-up on the dialog, and a scroll-snap fix in the room carousel. |

A patch that no longer matches **fails the build loudly** rather than silently
rendering the wrong thing.

**Option C needs neither.** Its `OVERRIDES` and `PATCHES` are both empty:

| | Option A | Option C |
| --- | --- | --- |
| Library component overrides | 4 | **0** |
| Library source patches | 4 | **0** |

A and B render the library's Browse Packages *page* and have to reshape its
parts. Option C renders its own board out of its own components, so there is no
library page to bend — and its build cannot break when the library moves. The
library components it does mount (`GlobalNav`, `AppStepper`, `DateRangeCalendar`,
`HotelDetailPage`, `CheckoutPage`, `ConfirmationPage`) are all used as shipped.

That last one matters: **every hotel-details link in Option C opens the library's
own `Hotel Details / Book Reservation` page template**, in a new tab, read-only —
the template's Reserve Room CTAs, back-to-results link and search band suppressed,
with a banner saying why.

### One open trade-off

The 300px branded hero pushes the first tile row just below the fold on a laptop,
which pulls against the feedback's *"packages visible without scrolling"*.
`EventHeaderBar` (~90px, no artwork) is kept and documented as the alternative —
swapping them is one line in `PackageGridScreen.vue`. Worth a decision at review.
