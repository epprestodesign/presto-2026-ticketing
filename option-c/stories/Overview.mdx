## What the feedback asked for

| Feedback | How Option C answers it |
| --- | --- |
| Grid, not a scrolling list | A 3-across grid of 6 tiles. The filter rail and result list are gone. |
| Packages below the header, no scrolling | Trade-off — see *The hero* below. A 300px branded hero with the search card tucked onto it; the compact ~90px strip is kept as the alternative. |
| One-click — no filtering, no options | A tile is a complete SKU. Selecting one raises a confirm dialog, then checkout. |
| Two-tier model per ticket type | 3 ticket tiers × 2 hotels, ordered so each row is one property. |
| Only variable: number of people | One guests dropdown, in the search bar, shared by the whole board. |
| Occupancy caps the ticket quantity | Occupancy caps tickets per **room**; a larger party books a second room. |
| "Ticket free, stay at this hotel" | The price charged is the stay. Tickets are $0, shown as the saving. |
| Detailed toggle/adjust UI is for later | It still exists — in Option A, untouched. Option C does not carry it. |

## The hero

The board leads with the branded event hero — scrim over the event artwork, the EventPipe
wordmark, the matchup and the date — with the search card tucked up onto its bottom edge, the
library's landing-page treatment.

It is rebuilt in `EventHero.vue` rather than mounting the library's `LandingPage`, which also
brings a booking widget, an ad rail and a "Who's Attending" section, none of which belong above a
one-click board. Option A mounts the whole page and overrides the background image to re-skin it;
Option C takes only the hero, so no library override is needed.

**This is a live trade-off, and worth naming.** The feedback asks for *"packages just below the
header, visible without scrolling"*; the branded hero was asked for separately. They pull against
each other:

| | Event Hero (mounted) | Event Header Bar (kept) |
| --- | --- | --- |
| Height | 300px | ~90px |
| Carries | artwork, wordmark, matchup, date | matchup, date, venue, stay dates |
| First tile row | just below the fold on a laptop | comfortably above it |

The library hero is 400px; this one runs 300px and lets the search card overlap it, which buys
back most of the difference. `EventHeaderBar` is still in the codebase and documented — swapping
them is a one-line change in `PackageGridScreen.vue`.

## The two universal controls

Dates and guests sit **above** the board, not on the tiles, because both re-price all six tiles
at once — six copies of either control would be six chances to disagree.

- **Check-in – Check-out → nights.** Nights multiply every room rate on the board. This is why
  the dates are up front: they change the price of every package simultaneously.
- **Guests → free tickets and rooms.** One free ticket per guest, and `ceil(guests / sleeps)`
  rooms, since occupancy caps a single room.

The library's own `BookingWidget` renders this pattern but **emits nothing** — its dates and
travelers are private state, which is why Option A had to patch the library to get a guest count
back out. Option C's bar owns the state and writes it to the journey store, so no library file is
touched. The picker itself is the library's `DateRangeCalendar`.

## How a tile is priced

```
rooms   = ceil(guests / occupancy)         one room only sleeps so many
price   = nightly × nights × rooms         ← what the guest pays
value   = price + ticket face × guests     ← struck through
saving  = ticket face × guests             ← "N tickets free"
```

Nights multiply the **room and nothing else** — the tickets stay free however long the stay runs,
so a three-night stay triples the price and leaves the saving unchanged. The nightly rate is the
contracted rate plus a tier uplift of roughly half the ticket's face value; the richer the tier,
the more the room carries. All prototype economics, and deterministic, so demos never drift.

## Badges, used sparingly

Every tile originally carried two hero badges. Both have been removed, because neither said
anything the tile didn't already:

- **"Premium / Value stay"** repeated the row heading three times per row — and was tinted with
  the *ticket tier's* accent, so one row showed the same "Value stay" in orange, red and blue as
  if they differed.
- **"Tickets free"** was true of all six tiles, and already stated in the header bar, the green
  facts line and the price note. A badge that is always on is not a badge.

The tile now takes an optional `flag` prop holding **at most one** badge, and the board hands it
to exactly one tile: the best value per guest — a comparison a guest cannot make at a glance
across six prices, two occupancies and a nights multiplier. It is navy, never the tier accent,
since the accent means "ticket tier" everywhere else on the board.

## Confirm, and (at the premium hotel) choose your room

Selecting a tile raises one dialog that does one of two jobs, decided by the hotel:

| Hotel | Room types | What the dialog does |
| --- | --- | --- |
| The Ritz-Carlton (premium) | 5 | Offers the **choice** — each room priced as a per-night difference against the room the package is priced around |
| Courtyard by Marriott (value) | 1 | Pure **confirmation** — exactly what you are buying, for these dates, at this price |

Either way this is a *confirmation* step, not a *configuration* one. The ticket tier, the hotel and
the free-ticket model stay baked into the tile — the guest is never asked to assemble a package,
only to see it before paying. That keeps the "no complex options" line intact while giving the
premium block the room choice it needs.

Choosing a smaller room can change the room **count**: a Deluxe King sleeps 2, so a party of four
in one takes two rooms, and the total follows.

## Hotel details — read-only, in its own tab

Every hotel name on the board — on the row heading and inside each tile — opens that property's
details page **in a new tab**, so the grid behind it keeps its dates and party size. Looking up a
hotel should never cost the guest their place in the flow.

It is the **library's own page template** — `Hotel Details / Book Reservation`
(`HotelDetailPage`): gallery, tabs, summary header, rooms, amenities, policies, map. Every link to
a hotel details page in this prototype uses it; nothing is hand-rolled.

Read-only means read-only. The template ships booking affordances — per-room "Reserve Room" CTAs,
a back-to-results link, a search band that would re-run a search — and all three are suppressed,
with a banner saying why. No stepper either: it is off-flow at stage `-1`. Same contract Option A's
read-only view holds.

## What is different from Option A

Option C is a fork of Option A, and the interesting part is what it **removes**:

- **No library page overrides.** Option A redirects four library files (`BookingWidget`,
  `PackageResultCard`, `PackageQuickViewDialog`, the hero image) because it renders the library's
  Browse Packages page and has to reshape its parts. Option C's `OVERRIDES` is empty — it renders
  its own board, so there is no library page to bend.
- **No source patches.** Option A patches four more library files as they're read. Option C's
  `PATCHES` is empty, so the build cannot break when the library moves.
- **No configuration state.** Option A's store carries `roomHotelId`, `roomTypeId`, `tierId` and
  `extraId`, all assembled in the modal. Option C's carries which tile, plus the shared stay —
  the dates and the party — because those are board-wide, not per-package.

The library components Option C mounts are `GlobalNav`, `AppStepper`, `DateRangeCalendar`,
`CheckoutPage` and `ConfirmationPage` — all used exactly as shipped.

## Scope

Grid → confirm → checkout → confirmation is clickable end to end. The whole stay is deep-linkable,
because all of it changes the price:

```
?screen=packages&from=2026/09/18&to=2026/09/21&guests=6   the board, 3 nights, 6 guests
?screen=packages&open=club-ritz                           the room-choice dialog (premium)
?screen=packages&open=mezz-courtyard                      the confirm dialog (value)
?screen=packages&open=club-ritz&roomType=executive-suite  a room picked in the dialog
?screen=checkout&pkg=club-ritz&guests=4                   a selection, ready to pay
?screen=hotelDetails&hotel=ritz                           the read-only reference view
```

A checkout link with no tile selected falls back to the board rather than rendering a package
nobody chose.

A la carte — pick your own hotel — is explicitly a **later, separate flow**, and is not in
Option C.
